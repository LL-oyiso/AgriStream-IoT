Overview

Agristream IoT provides smart monitoring for large commercial farms. Millions of soil sensors send telemetry in sudden surges during daylight hours, and drones upload bursts of high-resolution aerial images at the same time. The platform must accept these streams, store them and act on them (for example by starting irrigation) without losing data, and it must keep working when traffic jumps. I was asked to build a management web application and a scalable real-time processing system on Azure, and to prove with screenshots that everything runs online.

Solution

I designed and built an ASP.NET Core MVC management portal and a four-function serverless pipeline, deployed to Azure in South Africa North. Each Azure service has a specific job:

  • Azure App Service (Basic B1): hosts the MVC web app and, on the same plan, the Function App.
  • Azure SQL Database (Basic): stores user accounts with hashed passwords and the three system roles (Farmer, Agronomist, Admin), and the master registry of field devices.
  • Azure Blob storage: stores the drone images uploaded through the web app.
  • Azure Table storage: stores the high-frequency sensor readings, the image processing audit entries and the irrigation events.
  • Azure Storage queue: holds irrigation commands so that a surge of requests is absorbed and processed at a steady rate.
  • Azure Functions (four): a blob trigger that audits each uploaded image, an HTTP GET that returns the latest telemetry, an HTTP POST that queues an irrigation command, and a queue trigger that updates the device status in Azure SQL.

The result is a pipeline in which every stage is stateless, every request leaves evidence in a store I can show in the portal, and the compute can be scaled out to several instances.

Why this design and what the alternatives were. Splitting the work into four small functions means each stage scales and fails on its own. Putting a queue between the HTTP request and the database update means a surge of irrigation requests is absorbed by the queue and drained at a rate the Basic SQL database can handle, which is the queue-based load levelling that the brief's "without losing data" requirement needs. Calling SQL directly from the HTTP function would have been simpler, but a spike would then hit the database directly and drop requests. Event Hubs would suit millions of telemetry events per second, but it is not available on this subscription, so the web app simulator writes telemetry batches directly to Table storage. Queue delivery is at least once, so the queue function is idempotent: the command id is the primary key of the command log, and a repeated message is detected and ignored. A message that keeps failing is retried five times and then moved to the poison queue.

The rules I would configure on a Standard or higher plan

  • Scale out on CPU: add one instance when the average CPU percentage is above 70% over 5 minutes, with a 5-minute cooldown.
  • Scale out on memory: add one instance when the average memory percentage is above 80% over 5 minutes.
  • Scale in: remove one instance when the average CPU is below 30% over 10 minutes, with a 10-minute cooldown.
  • Limits: minimum 1, default 2 and maximum 5 instances.

Why these thresholds. I would scale out at 70% rather than 90% because a new instance takes a few minutes to provision and warm up, and at 90% requests are already queueing and response times have already suffered by the time help arrives. I would not scale out at 40% because the app would add instances for normal daily variation and cost more for no gain. The 5-minute window ignores short spikes but still reacts to a sustained surge, and memory at 80% protects against a leak or a large upload burst that CPU would not show. Scale-in is deliberately slower (10 minutes) and has a wide gap to the scale-out threshold, because with two instances at 30% the load on one remaining instance would be about 60%, which is below the 70% scale-out trigger; a narrower gap risks flapping, where the service scales in and then immediately out again (Microsoft, 2026b). Autoscale scales out when any scale-out rule is met and scales in only when all scale-in rules are met (Microsoft, 2026a). The minimum of one instance keeps costs low overnight, the default of two gives some resilience, and the maximum of five bounds the bill and, more importantly, the load on the Basic SQL database, which can only serve 30 concurrent workers (Microsoft, 2026i).

Worked example (illustrative numbers). If one instance normally runs at 35% CPU and a morning sensor surge doubles the traffic, the CPU reaches about 70% within a couple of minutes. After 5 minutes above the threshold the rule adds a second instance, and after it warms up each instance carries about 35% again. If the surge then triples the original load, the plan climbs back above 70% and a third instance is added. When the surge ends and CPU stays below 30% for 10 minutes, one instance is removed, then another after the cooldown, so the cost follows the traffic. The cost trade-off is that every extra B1 instance is billed for the time it runs, so the rules should add instances only when the CPU or memory signal justifies it.

Theory 1: Disaster recovery and redundancy

Question: Discuss Azure Storage redundancy options. Specifically compare locally redundant storage (LRS) with Geo-redundant storage (GRS). Explain which option would be the most appropriate for storing critical historical crop harvest records versus temporary sensor logs.

Agristream IoT holds two very different kinds of data. Sensor logs arrive in millions of small rows and lose value within days, while historical crop harvest records are small, permanent and impossible to recreate if lost. In my build the drone images, telemetry, audit rows and the irrigation queue all live in one Azure Storage account, and a storage account has a single redundancy setting that applies to Blob, Table, Queue and File storage alike (Microsoft, 2026g). Choosing that setting is therefore a disaster-recovery decision about what the business can afford to lose.

Azure Storage redundancy options

Description of service

Azure Storage always keeps multiple copies of data to protect it from hardware failures, outages and disasters. The options differ in where the copies are kept and how they are written (Microsoft, 2026g). Within the primary region there is locally redundant storage (LRS), which keeps copies in one datacenter, and zone-redundant storage (ZRS), which spreads them across three or more availability zones. Across regions there is geo-redundant storage (GRS), which adds an asynchronous copy in a paired secondary region, and geo-zone-redundant storage (GZRS), which combines ZRS in the primary region with that secondary copy. Read-access variants (RA-GRS and RA-GZRS) additionally let applications read from the secondary endpoint (Microsoft, 2026g).

Locally redundant storage (LRS)

Mechanism

LRS replicates data within a single physical datacenter in the chosen region and is designed for at least eleven nines (99.999999999%) of object durability over a year (Microsoft, 2026g). It protects against drive, server and rack failures. Its weakness is concentration: if a fire, flood or other disaster hits that datacenter, every replica of the account may be lost or unavailable (Microsoft, 2026g). In the outage scenarios Microsoft lists, LRS survives a failed node but not the loss of a whole datacenter or region (Microsoft, 2026g).

Where it adds value

LRS is the lowest-cost option, and Microsoft names it as a good choice when the data can easily be reconstructed if it is lost, or when governance rules keep data inside one region (Microsoft, 2026g).

Geo-redundant storage (GRS)

Mechanism

GRS first writes the data synchronously with LRS in the primary region, then copies it asynchronously to a secondary region hundreds of miles away, where it is again held with LRS. This gives at least sixteen nines of durability over a year (Microsoft, 2026g). Two consequences matter for design. First, the secondary copy is not readable unless the account is failed over, or unless it uses RA-GRS (Microsoft, 2026g). Second, because replication is asynchronous, the secondary lags the primary, so a regional failure can lose the most recent writes. The gap between the last write to the primary and the last write to the secondary is the recovery point objective (RPO), and an unplanned customer-managed failover is expected to lose data (Microsoft, 2026e; Microsoft, 2026g). This is the familiar replication-lag trade-off of asynchronous replication: the primary stays fast because it does not wait for the remote copy, at the price of a window in which a failover can lose acknowledged writes (Kleppmann, 2017).

Where it adds value

GRS survives a region-wide outage that LRS and ZRS cannot, which is why Microsoft recommends geo-replication for applications that need disaster recovery (Microsoft, 2026g). The price is higher storage cost and, after an outage, a failover step that updates the storage endpoints and leaves the data inaccessible while it runs (Microsoft, 2026g).

Comparing LRS with GRS

  • Failure covered: LRS covers disk, server and rack failure only. GRS also covers the loss of an entire datacenter or region (Microsoft, 2026g).
  • Durability: at least 11 nines for LRS and at least 16 nines for GRS (Microsoft, 2026g).
  • Cost: LRS is the cheapest option. GRS stores additional copies in a second region and costs more (Microsoft, 2026g).
  • Recovery behaviour: LRS has nothing to fail over to. GRS needs a failover to make the secondary writable, and an unplanned failover can lose recent data because replication is asynchronous (Microsoft, 2026e).
  • What neither protects against: every replica reflects the same current state, so a deletion or an overwrite is applied to all copies at once. Redundancy protects against hardware failure, not against data-modifying operations (Microsoft, 2026g).

Critical historical crop harvest records: GRS (or RA-GRS)

Harvest records are the long-term business asset of the platform. They support yield analysis, insurance claims and agronomic planning, they are written once and kept for years, and, unlike sensor readings, they cannot be recreated by the devices if they are lost. The cost of losing them is far higher than the extra storage cost of geo-replication, so GRS is the most appropriate choice. The asynchronous RPO is acceptable here because records are added slowly and are normally not changing at the moment of a disaster, so the window of unreplicated writes is small. If the dashboards must keep reading the history during a regional outage, RA-GRS adds a readable secondary endpoint, and GZRS or RA-GZRS would also remove the risk of losing a single datacenter inside the primary region (Microsoft, 2026g). Because replication also copies mistakes, these records still need soft delete or versioning and exports as a defence against accidental deletion, which redundancy alone does not give (Microsoft, 2026g).

Temporary sensor logs: LRS

Raw sensor readings arrive in huge volumes, are mostly useful for a short rolling window, and are continually replaced by new readings. If a datacenter were lost, the platform would lose only the most recent readings, the devices would keep reporting, and ingestion could resume in a healthy region. This is exactly the "data that can easily be reconstructed" case for which Microsoft names LRS as a good choice (Microsoft, 2026g). Paying to replicate millions of short-lived rows to a second region would add cost without protecting anything that the business cannot afford to lose.

How this applies to my Agristream build

My deployment uses one Standard storage account with LRS for everything, because the account's redundancy setting is shared by all of its services and my student subscription has no business case for geo-replication (Microsoft, 2026g). In production I would split the data across two storage accounts, which Microsoft recommends when resources have different redundancy requirements (Microsoft, 2026g). One GRS or RA-GRS account would hold the harvest records and archived imagery, and one LRS account would hold the telemetry table, the image audit table and the irrigation queue. The queue and audit rows are also transient: an irrigation command that is lost in a disaster is simply requested again, and my queue processing is idempotent because the command identifier is the primary key of the SQL command log, so a repeated message is detected and ignored.

Using the Two Options Together

The two options are not rivals but tools for different values of data. LRS keeps cost low where loss is cheap, and GRS spends money where loss is expensive. Separating the accounts lets Agristream apply each setting to the data that deserves it, and pairing GRS with versioning or soft delete covers both regional disasters and human error.

Theory 2: Stateless vs Stateful architecture

Question: Explain why it is critical to keep Azure App Services and Azure Functions stateless when designing applications for horizontal scaling. Discuss how storing session data or files locally on a web server instance negatively affects scale out behaviour.

The brief asks for a system that survives peak daylight surges, and the practical way to absorb a surge on Azure App Service is horizontal scaling: running the same app on more instances behind a load balancer. In my build the Web App and the Function App share one Basic B1 plan that I scale manually from one to three instances during the load test. That only works if every instance can serve every request, which is the property that statelessness gives.

Stateless and stateful applications

Description

A stateful component keeps data that later requests depend on in the memory or on the local disk of one particular server. A stateless component keeps no such data between requests. Anything that must persist lives in an external backing service such as a database, storage account or cache. The Twelve-Factor methodology states the rule directly: processes are stateless and share nothing, and the app never assumes that anything cached in memory or on disk will be available on a future request, because that request will probably be served by a different process (Wiggins, 2017). Microsoft gives the same advice for scalable Azure designs: avoid dependencies on a specific instance, do not assume that requests from the same source reach the same instance, and design services to be stateless where possible (Microsoft, 2026b). For Azure Functions the guidance is to write functions to be stateless (Microsoft, 2026c).

Why statelessness is critical for horizontal scaling

Mechanism

When a plan scales out, new instances start with empty memory and an empty local disk, and the load balancer spreads requests across all instances. When it scales in, instances are removed and whatever they held disappears. Even without scaling, hosted instances are expected to restart or move occasionally (Microsoft, 2026c). If requests depend on local state, three things go wrong. Requests that land on an instance without the state fail or behave differently. New instances add capacity but cannot take over existing users, so the extra capacity is wasted. And scale-in or a restart destroys state that users thought was safe. A stateless instance has none of these problems because it is interchangeable: adding an instance adds capacity immediately, and removing one loses nothing.

Statelessness for Azure Functions

The same reasoning applies to the queue-triggered function. Several instances can read the same queue as competing consumers, and no instance can assume which messages it will get (Hohpe and Woolf, 2004; Microsoft, 2026b). Queue delivery is at least once, so the function must also be idempotent, meaning a repeated message must not repeat its side effects (Microsoft, 2026b). My ProcessIrrigationCommand function holds no state of its own and writes to SQL with the command identifier as the primary key, so a redelivered message is rejected as a duplicate.

How locally stored session data hurts scale-out

Mechanism

In-memory session state is the classic example. If a user signs in on instance A and the session lives in A's memory, a later request routed to instance B finds no session, and the user appears to be signed out. The usual workaround is a "sticky session", which keeps routing the user to the same instance. The Twelve-Factor guidance calls sticky sessions a violation that should never be relied upon, and recommends keeping session data in a datastore with time-expiry such as Redis or Memcached (Wiggins, 2017). Sticky routing also undermines the purpose of scaling: it makes load uneven, and newly added instances receive only new users.

The ASP.NET Core data-protection example

Even apps that avoid explicit session state can depend on local state without noticing. ASP.NET Core protects authentication cookies, TempData and anti-forgery tokens with Data Protection keys, and by default each node has its own key ring, so a cookie encrypted on one node cannot be decrypted by another and sign-in fails intermittently (Microsoft, 2026j). On Azure App Service the platform persists the keys to the shared %HOME%\ASP.NET\DataProtection-Keys folder, which is synchronised across all instances of the app in a deployment slot, so one key ring serves every instance (Microsoft, 2026f). My app uses cookie authentication, and this shared key ring is why a user who signs in on one instance stays signed in when the load balancer sends the next request to another.

How locally stored files hurt scale-out

Mechanism

App Service has two kinds of file storage with very different behaviour across instances. The %HOME% content share is shared by all instances and persists across restarts, whereas the temporary local storage under %SystemDrive%\local is not shared between instances and is not persistent across restarts (Microsoft, 2026k). A file saved to local temporary storage on instance A therefore does not exist on instance B, so a user who uploads an image and then reloads the page may or may not see it depending on which instance answers. The shared %HOME% share avoids that particular problem, but it is a network share whose size is limited by the pricing tier and which every instance shares, so it is a poor place for large and growing volumes of drone imagery (Microsoft, 2026k). The scalable answer is to put files in a dedicated storage service.

How my build applies it

The drone-image upload streams the file straight from the request to Azure Blob Storage and writes nothing to the instance's disk. The blob-triggered function then reads the image from Blob Storage, so it does not matter which web instance accepted the upload or which function instance processes it.

Where state lives in Agristream

  • Users, roles and device status: Azure SQL Database.
  • Telemetry, image audit rows and irrigation events: Azure Table storage.
  • Drone images: Azure Blob storage.
  • Pending irrigation commands: an Azure Storage queue.
  • Sign-in state: an encrypted cookie, with the key ring on the shared %HOME% folder.

Every response from the web app also carries an X-Instance-Id header, and the load-test script counts the responses per instance, which gives measurable evidence that requests were served by several interchangeable instances during scale-out.

Statelessness and Scale-out Together

Statelessness is what makes extra instances useful, but it moves the pressure to the shared services. Microsoft warns that a database or other downstream service can limit throughput even when more compute instances are available, so the bottleneck must be identified before adding compute (Microsoft, 2026b). That applies directly to my build: the Basic SQL tier allows at most 30 concurrent workers (Microsoft, 2026i), so scaling stateless compute to three instances without tuning the queue function could overwhelm the database. Keeping the web tier and function tier stateless gives me the freedom to scale them, and measuring the shared services tells me when to stop. The same property is what lets a rule such as "add an instance when average CPU stays above 70%" work at all, because autoscale adds and removes identical instances according to a metric (Microsoft, 2026a).

Theory 3: Serverless Triggers and Bindings

Question: Using a table, compare Azure Functions triggers and input/output bindings. Include the following columns: Definition, Purpose, and an example of how each was used in your Agristream pipeline.

The Agristream pipeline has exactly four functions, and each one is defined by a trigger that makes it run and, in some cases, by bindings that move data in and out. The table compares the three concepts, followed by a discussion of when I used each and when I chose not to.

DefinitionPurposeExample in my Agristream pipeline
Trigger Defines how a function is invoked. A function has exactly one trigger, and the trigger can also pass data into the function (Microsoft, 2026l). To start the function in response to an event, such as a blob appearing, an HTTP request or a queue message, without any polling code of my own. All four functions: ProcessDroneImage (blob trigger on the drone-images container), GetLatestTelemetry (HTTP GET), QueueIrrigationCommand (HTTP POST) and ProcessIrrigationCommand (queue trigger on irrigation-commands).
Input binding A declarative connection to another resource that passes data into the function through a parameter. The trigger is itself a special type of input binding (Microsoft, 2026l). To give the function the data it needs without hard-coding access to the service, so connection details stay in configuration. The blob trigger binds the uploaded image to a BlobClient parameter, which the function uses to read the size, content type and metadata. The route value {fieldId} and the blob {name} are bound the same way.
Output binding A declarative connection that lets the function write data out to another resource, through a return value or an output property (Microsoft, 2026l). To send results to a service without writing client code, including creating the queue message in the correct encoding. QueueIrrigationCommand returns one object holding a [QueueOutput] message for the irrigation-commands queue and an [HttpResult] response, so a single invocation answers the browser and queues the command.

Triggers compared with bindings

Description of the differences

A trigger answers "what starts this function", and a function must have exactly one. Bindings answer "what data comes in and what goes out", they are optional, and a function can have several input and output bindings in any mix (Microsoft, 2026l). Because a trigger is a special input binding, it is the only one that causes execution. Both are declared with attributes on the method and its parameters in C#, and the connection is named by an app setting rather than written in code. In my functions the Connection = "AzureWebJobsStorage" setting is the only link to the storage account, which keeps secrets out of the source code.

How bindings add value to the pipeline

The output binding on QueueIrrigationCommand removes the code to create a queue client, serialise the message and encode it. The queue extension uses Base64 message encoding by default (Microsoft, 2026d), and the binding handles that for me, which avoids the encoding mismatch that otherwise makes a queue trigger fail on messages written by other code. The trigger on ProcessIrrigationCommand removes the polling loop, the visibility-timeout handling and the retry logic: a message is tried up to five times and then moved to a poison queue (Microsoft, 2026d).

When I used the SDK instead of a binding

Microsoft is explicit that bindings are optional and that a function can always create an Azure SDK client and use it directly (Microsoft, 2026l). I used the Table SDK directly, through a cached client factory, for the audit, telemetry and event tables. The telemetry function must query one partition at a time, page through results and stop after a limit, which a simple table binding does not give me. The partition design matters because a Table storage partition is served from one server with a scalability target of 2,000 entities per second (Microsoft, 2026h), so my keys use one partition per field per day. The trade-off is more code in exchange for control, whereas the blob trigger, the HTTP triggers and the queue output binding remove boilerplate without taking away any control I needed.

Triggers, bindings and scale

The trigger also decides how the function scales and needs tuning. For the queue trigger, batchSize (default 16) and newBatchThreshold (default 8 on a one-vCPU instance) set how many messages one instance processes at once, so the maximum concurrency per function per instance is their sum, 24 by default (Microsoft, 2026d). On three instances that is 72 concurrent database calls, more than the 30 concurrent workers the Basic SQL tier allows (Microsoft, 2026i). I therefore reduced the settings to a batch size of 6 and a threshold of 3, which gives 9 per instance and 27 across three instances, and recorded the before-and-after results in the load-test section. The queue itself acts as a buffer between the fast HTTP producer and the slower, throttled consumer, which is the Message Channel and Competing Consumers pattern described by Hohpe and Woolf (2004).

Triggers and Bindings Together

In Agristream the triggers decide when work happens, the bindings decide how data moves with the least code, and the SDK fills the gaps where I need control. Using the right mix is what keeps the four functions small, configurable and safe to scale.
