CLDV7112 Practicum: Step-by-step portal guide

This guide takes you from an empty resource group to a deployed, tested and screenshotted Agristream system. Do the steps in order. Every green box is a screenshot you must take at that moment, and the number matches the figure number in your submission document. The master checklist is at the end.

0. Golden rules

Read these first.
1. Use the resource group your institution gave you. Never create or delete a resource group.
2. Region: South Africa North for everything.
3. Operating system: Windows for both the Web App and the Function App.
4. Application Insights: turn it Off or choose No whenever the wizard offers it (it is not available on this subscription and the wizard will fail).
5. App Service plan: Basic B1 only. Standard and above are blocked by policy.
6. Name everything with your student number so it is unique and the web address is correct.
7. Secrets (passwords, connection strings, keys) live only in Notepad and in the portal app settings. Never in a screenshot, in the code or in git. When you screenshot app settings, leave the values hidden.

1. How the system fits together

The browser talks to the MVC Web App. The Web App stores users in Azure SQL, stores images in Blob storage and calls two HTTP functions in the Function App for telemetry (GET) and irrigation (POST). The POST function drops a message on the storage queue. The queue function reads the message and updates the device in Azure SQL. The blob function fires when an image arrives and writes an audit row to Table storage. The Web App and the Function App share one Basic B1 plan and one storage account.

2. What this subscription allows

Available: Microsoft.Web (App Service, Functions), Microsoft.Storage, Microsoft.Sql.
Not available: Microsoft.Insights (Application Insights, autoscale rules, alerts), Azure Load Testing, Standard or higher App Service plans. Section 10 shows how to attempt these on purpose so you have refusal screenshots.

Step 13. Load test: baseline (section E)

Make sure the plan is on 1 instance and host.json is on the baseline values 16 and 8 (as published). Start with an empty queue and an empty IrrigationCommandLog table so the numbers are clean: in the Query editor run query K (DELETE FROM dbo.IrrigationCommandLog) and reset the device statuses if you want.

1. Open PowerShell in the Agristream folder.
2. Put the key in an environment variable for this window only:

$env:AGRISTREAM_SIM_KEY = Read-Host "SimulatorKey"

3. Run the baseline (about 3 minutes):

.\scripts\load-test.ps1 -StudentNumber YOUR_SN -Users 50 -DurationSeconds 120 -SensorBurst 5000 -ImageBurst 50 -Label baseline-1-instance

4. Immediately switch to the Evidence page (admin) and refresh while it runs. Screenshot at the peak backlog. Screenshot the final printed summary, and copy the numbers into Notepad (throughput, p50, p95, p99, failures, peak backlog, drain time).
5. Also take the Simulator screenshots (a burst of images).

{{FIG:sim-burst}} {{FIG:load-baseline}} {{FIG:evidence-peak}}

Fix it: if the script says 404, the SimulatorKey setting is empty or does not match. If many requests fail with 5xx, lower -Users to 30 and note it in the write-up. If PowerShell blocks the script run: powershell -ExecutionPolicy Bypass -File .\scripts\load-test.ps1 ...

Step 15. Optimise: tune the queue trigger (section E)

1. Open Agristream.Functions\host.json and screenshot the baseline values (batchSize 16, newBatchThreshold 8).
2. Change them to batchSize 6 and newBatchThreshold 3. Screenshot again.
3. Republish the Function App (Step 6).
4. Rebuild confidence: each instance now runs at most 9 queue messages at once, so 3 instances run 27, below the 30 concurrent worker limit of Azure SQL Basic.
5. If you saw errors in the baseline, screenshot where they appear (the load-test output or the SQL "resource limit" message). If you never saw the throttle, skip that figure, it is optional.
