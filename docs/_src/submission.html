Overview

Agristream IoT provides smart monitoring for large commercial farms. Millions of soil sensors send telemetry in sudden surges during daylight hours, and drones upload bursts of high-resolution aerial images at the same time. The platform must accept these streams, store them and act on them (for example by starting irrigation) without losing data, and it must keep working when traffic jumps. I was asked to build a management web application and a scalable real-time processing system on Azure, and to prove with screenshots that everything runs online.

Solution

I designed and built an ASP.NET Core MVC management portal and a four-function serverless pipeline, deployed to Azure in South Africa North. Each Azure service has a specific job:

  • Azure App Service (Basic B1): hosts the MVC web app and, on the same plan, the Function App.
  • Azure SQL Database (Basic): stores user accounts with hashed passwords and the three system roles (Farmer, Agronomist, Admin), and the master registry of field devices.
  • Azure Blob storage: stores the drone images uploaded through the web app.
  • Azure Table storage: stores the high-frequency sensor readings, the image processing audit entries and the irrigation events.
  • Azure Storage queue: holds irrigation commands so that a surge of requests is absorbed and processed at a steady rate.
  • Azure Functions (four): a blob trigger that audits each uploaded image, an HTTP GET that returns the latest telemetry, an HTTP POST that queues an irrigation command, and a queue trigger that updates the device status in Azure SQL.

The result is a pipeline in which every stage is stateless, every request leaves evidence in a store I can show in the portal, and the compute can be scaled out to several instances.

B. Relational Database (User Management)

I created an Azure SQL database to manage user accounts and the assigned system roles, and connected the MVC app to it through the SqlConnectionString setting.

{{FIG:sql-overview}} {{FIG:sql-firewall}} {{FIG:sql-tables}}

The Users table holds the username, a salted password hash and the role, with a check constraint that only allows Farmer, Agronomist or Admin. The evidence chain for the connection is: register in the app, sign in, then see the same rows in the database and in the Admin page.

{{FIG:register}} {{FIG:login}} {{FIG:sql-users}} {{FIG:admin-users}}

Why Azure SQL and how it is secured. User accounts and roles are relational data with uniqueness and integrity rules, so Azure SQL is a better fit than Table storage. Passwords are never stored in clear text: the app stores a salted PBKDF2 hash. Admin accounts cannot be self-registered, because the Register page only offers Farmer and Agronomist and an Admin assigns the Admin role. The same database also holds the device registry that the queue function updates, so the user data and the operational data are both in one transactional store.

C. Cloud storage (Data and Media)

I used both unstructured and NoSQL storage in one Standard LRS storage account.

{{FIG:storage-overview}}

Azure Blob storage (drone images)

Drone images uploaded through the web app are streamed straight into a private drone-images container with the field and uploader recorded as blob metadata. Nothing is saved to the web server's disk.

{{FIG:blob-container}} {{FIG:upload-page}}

Azure Table storage (telemetry, audit and events)

Sensor readings are stored in the SensorReadings table. The partition key combines the field and the day, so writes spread over many partitions and each partition stays within its throughput target, and the row key uses reverse ticks so the newest readings are returned first.

{{FIG:table-sensor}}

Why these two services. Blob storage is built for large binary objects such as images, and it is cheap and scales without limit. Table storage is a schemaless key-value store designed for very large volumes of simple rows with fast key lookups, which suits telemetry. Azure Cosmos DB would be a richer NoSQL alternative, but its resource provider is not registered on this subscription, and Table storage is sufficient for the access pattern of "latest readings for one field". Azure SQL would have forced a schema and costs far more per row at this volume.

D. Serverless data pipeline

The pipeline uses exactly four Azure Functions, one for each required trigger type.

D1. Blob-triggered function (ProcessDroneImage)

When a drone image lands in the container, this function logs the upload details and writes a processing-status audit entry to Table storage. The chain is: upload, function log, audit row, then the status shown back in the web app.

{{FIG:logstream-blob}} {{FIG:table-audit}} {{FIG:upload-processed}}

D2. HTTP-triggered function, GET (GetLatestTelemetry)

When a farmer opens a field dashboard, the MVC app calls this function with the field id. It reads the newest rows from the telemetry table and returns them as JSON, so the dashboard renders without any heavy query in the web tier.

{{FIG:get-json}} {{FIG:dash-telemetry}}

D3. HTTP-triggered function, POST (QueueIrrigationCommand)

When a user clicks Trigger irrigation, or the sensor simulator detects a dry-soil anomaly, the MVC app calls this function. It validates the request and places an irrigation command message on the irrigation-commands queue using a queue output binding, then answers with HTTP 202 and the command id.

{{FIG:dash-trigger}} {{FIG:queue-message}}

D4. Queue-triggered function (ProcessIrrigationCommand)

This function listens to the queue, processes each command and updates the device's operational status in the master registry table in Azure SQL. It also records the event in Table storage.

{{FIG:dash-before}} {{FIG:dash-after}} {{FIG:sql-commandlog}} {{FIG:table-events}} {{FIG:logstream-queue}}

Why this design and what the alternatives were. Splitting the work into four small functions means each stage scales and fails on its own. Putting a queue between the HTTP request and the database update means a surge of irrigation requests is absorbed by the queue and drained at a rate the Basic SQL database can handle, which is the queue-based load levelling that the brief's "without losing data" requirement needs. Calling SQL directly from the HTTP function would have been simpler, but a spike would then hit the database directly and drop requests. Event Hubs would suit millions of telemetry events per second, but it is not available on this subscription, so the web app simulator writes telemetry batches directly to Table storage. Queue delivery is at least once, so the queue function is idempotent: the command id is the primary key of the command log, and a repeated message is detected and ignored. A message that keeps failing is retried five times and then moved to the poison queue.

E. Load testing

I simulated heavy traffic with the sensor simulator, the drone-image simulator and scripts/load-test.ps1. The script runs a configurable number of concurrent virtual users for a set time. Each user rotates through a health check, a CPU-bound request so the plan's CPU metric rises, a call to the GET function (as the dashboard does) and a call to the POST function (which fills the queue). It then polls the queue until it is empty and prints the throughput, latency percentiles, failures, peak backlog, drain time and requests per instance.

Optimisation

After the baseline I scaled the plan out to three instances and tuned the queue trigger. The default queue settings let each instance process up to 24 messages at once (a batch size of 16 plus a threshold of 8), which on three instances is 72 concurrent database calls, more than the 30 concurrent workers that the Basic SQL tier allows, so extra instances could cause throttling instead of more throughput. I reduced the batch size to 6 and the threshold to 3, which is 9 per instance and 27 across three instances.

G. Autoscaling

The brief asks for rules that scale out the App Service based on CPU or memory. The Basic B1 plan only offers manual scaling, and rule-based autoscale (Azure Monitor autoscale) also needs a resource provider and a tier the subscription does not allow. I recorded the attempts, then scaled the shared plan out manually from one to three instances during the load test.

{{FIG:scale-blade}} {{FIG:attempt-autoscale}} {{FIG:attempt-scaleup}} {{FIG:scale-3}} {{FIG:scale-cpu}} {{FIG:instance-split}}

The CPU chart split by instance and the per-instance request counts show the traffic being shared across the three instances after the scale-out.

The rules I would configure on a Standard or higher plan

  • Scale out on CPU: add one instance when the average CPU percentage is above 70% over 5 minutes, with a 5-minute cooldown.
  • Scale out on memory: add one instance when the average memory percentage is above 80% over 5 minutes.
  • Scale in: remove one instance when the average CPU is below 30% over 10 minutes, with a 10-minute cooldown.
  • Limits: minimum 1, default 2 and maximum 5 instances.

Why these thresholds. I would scale out at 70% rather than 90% because a new instance takes a few minutes to provision and warm up, and at 90% requests are already queueing and response times have already suffered by the time help arrives. I would not scale out at 40% because the app would add instances for normal daily variation and cost more for no gain. The 5-minute window ignores short spikes but still reacts to a sustained surge, and memory at 80% protects against a leak or a large upload burst that CPU would not show. Scale-in is deliberately slower (10 minutes) and has a wide gap to the scale-out threshold, because with two instances at 30% the load on one remaining instance would be about 60%, which is below the 70% scale-out trigger; a narrower gap risks flapping, where the service scales in and then immediately out again (Microsoft, 2026b). Autoscale scales out when any scale-out rule is met and scales in only when all scale-in rules are met (Microsoft, 2026a). The minimum of one instance keeps costs low overnight, the default of two gives some resilience, and the maximum of five bounds the bill and, more importantly, the load on the Basic SQL database, which can only serve 30 concurrent workers (Microsoft, 2026i).

Worked example (illustrative numbers). If one instance normally runs at 35% CPU and a morning sensor surge doubles the traffic, the CPU reaches about 70% within a couple of minutes. After 5 minutes above the threshold the rule adds a second instance, and after it warms up each instance carries about 35% again. If the surge then triples the original load, the plan climbs back above 70% and a third instance is added. When the surge ends and CPU stays below 30% for 10 minutes, one instance is removed, then another after the cooldown, so the cost follows the traffic. The cost trade-off is that every extra B1 instance is billed for the time it runs, so the rules should add instances only when the CPU or memory signal justifies it.

An autoscale setting for this rule set looks like this (ARM-style, shortened):

{
  "profiles": [{
    "name": "default",
    "capacity": { "minimum": "1", "maximum": "5", "default": "2" },
    "rules": [
      { "metricTrigger": { "metricName": "CpuPercentage", "operator": "GreaterThan", "threshold": 70,
          "timeAggregation": "Average", "timeWindow": "PT5M", "statistic": "Average", "timeGrain": "PT1M" },
        "scaleAction": { "direction": "Increase", "type": "ChangeCount", "value": "1", "cooldown": "PT5M" } },
      { "metricTrigger": { "metricName": "MemoryPercentage", "operator": "GreaterThan", "threshold": 80,
          "timeAggregation": "Average", "timeWindow": "PT5M", "statistic": "Average", "timeGrain": "PT1M" },
        "scaleAction": { "direction": "Increase", "type": "ChangeCount", "value": "1", "cooldown": "PT5M" } },
      { "metricTrigger": { "metricName": "CpuPercentage", "operator": "LessThan", "threshold": 30,
          "timeAggregation": "Average", "timeWindow": "PT10M", "statistic": "Average", "timeGrain": "PT1M" },
        "scaleAction": { "direction": "Decrease", "type": "ChangeCount", "value": "1", "cooldown": "PT10M" } }
    ]
  }]
}

Autoscaling the web tier is only part of the story. The queue-consuming function app shares the same plan, so its instances scale with the plan, and the database must be sized for the maximum instance count, which is why the queue batch settings are tuned as shown in section E.
